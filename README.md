# Умный дом — MVP мини-приложения в MAX

Цифровое решение для жителей МКД и управляющей организации: подача заявок,
передача и оплата показаний счётчиков, оплата ЖКУ — и диспетчерская панель УК,
которая принимает заявки, назначает специалистов и уведомляет жителя.

## Живое демо и доступ

Приложение развёрнуто и доступно онлайн:

- Мини-приложение жителя: **https://smart-home-nwbx.onrender.com/**
- Диспетчерская УК (для сотрудников): **https://smart-home-nwbx.onrender.com/admin**
  - Вход по паролю: `Dispetcher2026` (значение переменной `ADMIN_PASSWORD`).

Внутри MAX мини-приложение открывается из чат-бота (вход по подписи запуска). По
прямой ссылке в обычном браузере приложение жителя открывается в демо-режиме
(включён `ALLOW_DEMO_LOGIN=1`), поэтому его можно посмотреть и без MAX.

> Хостинг — бесплатный тариф Render: после ~15 минут простоя сервис засыпает,
> первый заход после этого занимает ~30-50 секунд (потом быстро). Тестовые данные
> при перезапуске сбрасываются к исходным.

## Как пользоваться

Житель (мини-приложение):
- «Заявки» → «+» — подать заявку на ремонт (тип, описание, специалист, время).
  Открыть заявку из списка — виден статус-таймлайн; кнопка «Пожаловаться» создаёт жалобу.
- «Заявки» → переключатель «Жалобы» → «+» — подать жалобу (тема + текст).
- «Счётчики» — ввести и отправить показания.
- «Платежи» — посмотреть начисления и оплатить.
- Колокольчик на главной — уведомления от УК.

Диспетчер (панель `/admin`, вход по паролю):
- «Заявки» — открыть новую, назначить специалиста и время («Взять в работу»),
  писать жителю, отметить выполненной.
- «Жалобы» — открыть жалобу и отправить ответ жителю.
- «Показания» — переданные жителями значения с расходом.
- Действия житель ↔ диспетчер синхронизируются в реальном времени; жителю уходит
  уведомление в MAX (или в консоль сервера, если бот без токена).

## Назначение решения

Житель дома из мессенджера MAX (через чат-бота открывает мини-приложение):
сообщает о проблеме (авария, вывоз мусора, освещение, домофон, лифт), передаёт
показания счётчиков, видит начисления и оплачивает ЖКУ, следит за статусом заявок.
Житель также подаёт жалобы (на качество работ, сроки, поведение сотрудника, поборы,
уборку) — отдельно от заявок на ремонт. Диспетчер УК в отдельной панели видит все
заявки и жалобы, назначает мастера и время визита, отвечает на жалобы — уведомление
приходит жителю в MAX. Обе стороны работают с общими данными, статусы синхронизируются
в реальном времени.

## Что умеет (функции)

Житель (мини-приложение):
- Подать заявку на ремонт: тип проблемы, описание, желаемый специалист и время.
- Следить за статусом заявки: таймлайн «принята → специалист назначен → в пути → выполнена».
- Подать жалобу (тема + текст, можно привязать к заявке) и получить ответ диспетчера.
- Передать показания счётчиков (с расчётом расхода) и оплатить ЖКУ.
- Получать уведомления от УК (в MAX и в приложении).

Диспетчер (панель УК):
- Заявки: список с фильтрами, назначение специалиста и времени, сообщения жителю, закрытие.
- Жалобы: список открытых/отвеченных, чтение и ответ жителю.
- Показания: переданные жителями значения с расходом.

## Основной пользовательский сценарий

1. Житель открывает мини-приложение из чат-бота MAX (вход по подписи запуска).
2. На вкладке «Заявки» нажимает «+», выбирает категорию (например, «Авария»),
   описывает проблему и отправляет.
3. Заявка мгновенно появляется у диспетчера со статусом «Новая».
4. Диспетчер открывает заявку, назначает специальность и имя мастера, выбирает
   время визита, нажимает «Взять в работу и уведомить жителя».
5. Жителю приходит уведомление в MAX «Мастер придёт …», статус меняется на
   «В работе», событие видно на главном экране.
6. Диспетчер отмечает заявку выполненной — статус у жителя становится «Выполнено».

Дополнительно: передача показаний счётчиков (с расчётом расхода) и оплата ЖКУ.

## Состав и архитектура решения

```
frontend/public/        Мини-приложение жителя (index.html) и панель диспетчера (admin.html).
                        Статические HTML/CSS/JS (ES-модули), без сборки.
  ├─ styles.css         Общие стили.
  ├─ icons.js           SVG-иконки.
  ├─ api.js             REST-клиент + подписка на живые обновления (SSE).
  ├─ bridge.js          Обёртка над MAX Bridge (получение стартовых данных).
  ├─ index.html/.js     Экраны жителя: Главная, Счётчики, Платежи, Заявки.
  └─ admin.html/.js     Диспетчерская: список/карточка заявки, показания.

backend/src/            Node.js + Express.
  ├─ server.js          REST API, SSE, раздача статики, уведомления.
  ├─ db.js              Файловое хранилище (JSON). Заменяется на PostgreSQL при масштабировании.
  ├─ seed.js            Тестовые (демо) данные и вывод ленты событий.
  └─ max/
      ├─ validate.js    Проверка подписи стартовых данных мини-приложения (WebAppData).
      └─ bot.js         Bot API MAX: long polling и отправка сообщений (заглушка без токена).
```

Логика разделена: раздача данных (API) отделена от их хранения (db.js) и от интеграции
с MAX (max/*), фронтенд общается с бэкендом только по REST + SSE.

## Запуск через Docker (одна команда)

```bash
cp .env.example .env      # при необходимости впишите MAX_BOT_TOKEN
docker compose up --build
```

Откройте:
- мини-приложение жителя — http://localhost:3000/
- диспетчерская панель — http://localhost:3000/admin (вход для сотрудника,
  пароль по умолчанию `admin`, меняется в `.env` → `ADMIN_PASSWORD`)

Роли разделены: житель работает в мини-приложении (открывается из MAX),
диспетчерская — отдельная панель для сотрудников УК со входом по паролю.
Перекрёстных ссылок между ролями нет.

## Запуск без Docker

```bash
npm install
npm start
```

По умолчанию `npm start` не читает `.env` (это делает Docker). Есть два режима:

- DEV (для локального просмотра в браузере): просто `npm start`. Токен не задан →
  вход как демо-житель, `/admin` — по паролю (по умолчанию `admin`).
- MAX/боевой (проверка подписи + реальные сообщения бота): передать переменные, напр.
  ```bash
  node --env-file=.env backend/src/server.js
  ```
  (или задать `MAX_BOT_TOKEN` в окружении перед `npm start`). С токеном приложение
  жителя в обычном браузере вернёт 401 — оно откроется только из MAX, если не задан
  `ALLOW_DEMO_LOGIN=1`.

Диспетчерская `/admin` требует пароль из `ADMIN_PASSWORD` (по умолчанию `admin`).

## Подключение к реальному MAX (пошагово)

1. Токен бота. Скопируйте `.env.example` в `.env` и впишите токен команды:
   ```
   MAX_BOT_TOKEN=<токен из кабинета business.max.ru>
   MINIAPP_URL=<https-адрес мини-приложения, см. шаг 2>
   ```
   С заданным токеном включается проверка подписи входа и реальная отправка
   сообщений жителю ботом; без токена — DEV-режим (демо-житель, сообщения в консоль).

2. HTTPS для мини-приложения. MAX открывает мини-приложение только по HTTPS.
   Локально поднимите туннель на порт 3000:
   ```bash
   npm start                 # терминал 1
   npx ngrok http 3000       # терминал 2 — даст адрес https://xxxx.ngrok-free.app
   ```
   Этот https-адрес впишите в `MINIAPP_URL` и перезапустите сервер.

3. Привязать адрес к боту. В кабинете business.max.ru: «Чат-бот и мини-приложение»
   → «Настроить» → поле URL → вставьте https-адрес из ngrok. В чате с ботом появится
   кнопка запуска мини-приложения.

4. MAX Bridge уже подключён в `index.html` (скрипт `https://st.max.ru/js/max-web-app.js`):
   внутри MAX появляется `window.WebApp`, приложение берёт стартовые данные и шлёт их
   на `/api/auth`, где сервер проверяет подпись (`backend/src/max/validate.js`).

5. Проверка внутри MAX: откройте мини-приложение из бота, создайте заявку и жалобу →
   в диспетчерской они появятся → назначьте мастера / ответьте на жалобу → жителю
   придёт сообщение от бота в MAX.

Актуальные параметры API MAX сверяйте с документацией dev.max.ru (платформа меняется).

## Необходимые параметры окружения / переменные окружения

| Переменная          | Назначение                                             | По умолчанию                    |
|---------------------|--------------------------------------------------------|---------------------------------|
| `MAX_BOT_TOKEN`     | Токен чат-бота MAX. Пусто → DEV-режим (демо-житель).   | (пусто)                         |
| `ADMIN_PASSWORD`    | Пароль входа в диспетчерскую панель `/admin`.          | `admin`                         |
| `ALLOW_DEMO_LOGIN`  | `1` — открывать приложение жителя вне MAX как демо (для показа по ссылке). | `0` |
| `MAX_API_BASE`      | База Bot API MAX.                                      | `https://platform-api.max.ru`   |
| `MINIAPP_URL`       | HTTPS-URL мини-приложения (кнопка «Открыть» в боте).  | (пусто)                         |
| `PORT`              | Порт HTTP-сервера.                                     | `3000`                          |
| `DATA_DIR`          | Каталог файлового хранилища.                           | `./backend/data`                |
| `LAUNCH_MAX_AGE_SEC`| Макс. возраст стартовых данных MAX (replay-защита).   | `86400`                         |

## Используемые порты

- `3000` — HTTP (API + статика + SSE).

## Зависимости

- Node.js 20+.
- `express` (единственная runtime-зависимость; версии зафиксированы в `package-lock.json`).
- Остальное — встроенные модули Node (`crypto`, `fetch`, `fs`).

## Внешние сервисы и интеграции

- **MAX Bot API** (`https://platform-api.max.ru`) — авторизация по заголовку
  `Authorization`, методы отправки сообщений и получения обновлений (long polling).
- **MAX Bridge** — стартовые данные пользователя на стороне клиента.
- Проверка подписи запуска — по алгоритму dev.max.ru/docs/webapps/validation
  (`secret_key = HMAC-SHA256('WebAppData', BOT_TOKEN)`, затем подпись отсортированных
  параметров и сравнение с `hash`). `user_id` берётся только из провалидированных данных.

## Описание работы с данными

Данные хранятся в JSON-файле (`DATA_DIR/db.json`), создаётся при первом запуске из
`seed.js`. Сущности: пользователи, начисления и история платежей, каталог счётчиков и
переданные показания, заявки, жалобы, уведомления. Для продакшена файловое хранилище
заменяется на СУБД без изменения API-контракта.

## Порядок работы с тестовыми данными

Реальной интеграции с ГИС ЖКХ и MAX в MVP нет — данные тестовые, подготовлены заранее
и обезличены. Это указано в интерфейсе. Без `MAX_BOT_TOKEN` вход в мини-приложение
проходит в DEV-режиме (демо-житель «Анна»), а уведомления бота пишутся в консоль сервера.
С заданным токеном включается проверка подписи запуска и реальная отправка сообщений.

## Пошаговый сценарий проверки

1. `docker compose up --build` (или `npm install && npm start`).
2. Открыть http://localhost:3000/ (житель) и http://localhost:3000/admin (диспетчер)
   в двух вкладках. В диспетчерскую войти по паролю `ADMIN_PASSWORD` (по умолчанию `admin`).
3. У жителя: «Заявки» → «+» → «Авария» → описать → «Отправить заявку».
4. Убедиться, что заявка появилась у диспетчера как «Новая» (без перезагрузки).
5. У диспетчера: открыть заявку → указать мастера и время → «Взять в работу».
6. Убедиться, что у жителя статус стал «В работе» и пришло сообщение о времени визита.
7. У диспетчера: «Отметить выполненной» → у жителя статус «Выполнено».
8. Жалоба: у жителя «Заявки» → «Жалобы» → «+» → тема + текст → отправить; у диспетчера
   вкладка «Жалобы» → открыть → ответить; ответ появляется у жителя.
9. Проверить «Счётчики» (передать показания) и «Платежи» (оплатить) у жителя;
   показания появляются во вкладке «Показания» у диспетчера.

## Примеры ожидаемого поведения системы

- Создание заявки → `POST /api/requests` → событие `request.created` по SSE обоим клиентам.
- Назначение мастера → `PATCH /api/requests/:id {action:"dispatch"}` → статус `progress`,
  сообщение жителю (в MAX или в консоль), событие `request.updated`.
- Передача показаний с новым значением меньше предыдущего → ответ 400 с понятной ошибкой.

## Известные ограничения

- Файловое хранилище и один демо-житель — рассчитано на MVP, не на нагрузку.
- Вход диспетчера — по общему паролю (`ADMIN_PASSWORD`), токен сессии хранится в
  памяти сервера (сбрасывается при перезапуске). Для продакшена — полноценные учётки.
- Интеграции с ГИС ЖКХ / реестрами не подключены — используются тестовые данные.
- Фронтенд сделан на статических ES-модулях; для продакшена его можно пересобрать на
  React + MAX UI без изменения API-контракта.

## Деплой (как развёрнуто онлайн)

Проект развёрнут на Render (бесплатный Web Service) прямо из этого репозитория:

- Branch: `final`
- Build Command: `npm install`
- Start Command: `npm start`
- Instance Type: Free
- Переменные окружения в панели Render: `MAX_BOT_TOKEN`, `ADMIN_PASSWORD`,
  `ALLOW_DEMO_LOGIN=1` (переменную `PORT` Render задаёт сам).

Сервер слушает порт из `PORT`, фронтенд и API отдаются с одного адреса — поэтому
подходит любой хостинг Node без доработок. Секреты (токен, пароль) хранятся в
настройках хостинга, а не в репозитории.
